# Отчёт: автономное чтение геометрии из КОМПАС‑3D и план обработки

**Проект:** TrochoidCam (KompasTrochoidCam)
**Ветка:** `arena/a86018b8-trochoidcam` → `develop`
**Проверено на:** КОМПАС‑3D v19 (19.0.11), Windows x64
**Дата отчёта:** 25.10.2026

---

## 1. Коротко

Приложение подключается к **уже запущенному** КОМПАС‑3D отдельным процессом, читает геометрию активной детали, показывает её в своём окне и позволяет построить план фрезерной обработки вплоть до управляющей программы.

Главный практический результат последнего этапа: **приложение больше не падает при подключении**. На машине заказчика подтверждено: подключение к КОМПАС v19 x64 и чтение геометрии реальной детали (`Прижим 100x28 М6 V3 28mm.m3d`) работают.

Ранее процесс завершался фатально (`System.ExecutionEngineException`) сразу после нажатия «Подключиться к КОМПАС» — причиной был неверный способ вызова COM‑интерфейсов API 7. Способ заменён на API 5, где все интерфейсы Automation‑совместимые и вызываются штатно.

## 2. Что сделано

### 2.1. Подключение к КОМПАС‑3D

| Что | Как реализовано |
|---|---|
| Поиск запущенного КОМПАС | CLSID берётся из реестра по ProgID (не зашит в код): `KOMPAS.Application.7`, затем `.6/.5`, затем `KOMPAS.Application`; далее `GetActiveObject` (Running Object Table) |
| Запасной путь | Обход ROT с фильтром по CLSID и по признаку «объект приложения» |
| Отсутствие КОМПАС | Приложение не падает: показывает демо‑деталь и внятное сообщение в строке статуса |
| Причины неудачи | Собираются в отчёт «Диагностика»: что зарегистрировано в реестре, какие процессы КОМПАС запущены, разрядность и права нашего процесса, HRESULT каждой попытки |

Отдельный момент, выяснившийся при отладке: объект, который отдаёт API 7 (`IApplication`), **не является** приложением API 5 — у него нет `ActiveDocument3D`, а метод `CastTo` в v19 отсутствует. Поэтому API 5 подключается **отдельно**, по собственному ProgID `KOMPAS.Application.5` (он зарегистрирован: `{6b0b5194-4acd-4095-9bc1-11179fbbb05a}`), и проверяется именно вызовом `ActiveDocument3D`.

### 2.2. Чтение геометрии детали

Цепочка вызовов (все интерфейсы — Automation/`IDispatch`, ссылки на библиотеки КОМПАС при сборке не нужны):

```
KOMPAS.Application.5
  └ ActiveDocument3D()                 ksDocument3D
      └ GetPart(pTop_Part = -1)        ksPart        (запасные индексы: 0, 1)
          └ BodyCollection()           ksBodyCollection → ksBody[]
              └ FaceCollection()       ksFaceCollection → ksFaceDefinition[]
                  ├ LoopCollection()           циклы грани
                  │   ├ IsOuter()              внешний / внутренний (отверстие)
                  │   └ EdgeCollection()       рёбра цикла
                  │       └ GetCurve3D()       ksEdgeDefinition → ksCurve3D
                  │           └ CalculatePolygon(0.2)   массив x,y,z с шагом 0.2 мм
                  └ (запасной путь) GetVertex(true/false) → две вершины ребра
```

Что получается в результате:

- **только плоские горизонтальные грани** — разброс Z по всем точкам грани ≤ 0.05 мм (для 2.5D‑фрезерования по Z‑уровням остальное не нужно);
- у каждой грани — **все циклы** (внешний контур и отверстия) с корректным признаком `IsOuter`;
- **рёбра** — отрезки и дуги: кривая раскладывается полигоном с шагом 0.2 мм, затем по трём точкам подбирается окружность; замкнутое круговое ребро даёт полный оборот 2π;
- рёбра **дедуплицируются** (одно ребро читается из двух соседних граней), ключ не зависит от направления обхода;
- контуры **сшиваются** из кусков по ближайшим концам — порядок и направление рёбер в API не гарантированы, а для построения области это критично.

Дополнительно, поверх геометрии:

- **область обработки** — площадь и глубина по выбранным граням/рёбрам, **объём снимаемого металла** (площадь × глубина, в см³);
- **дерево плана обработки**: `План фрезерной обработки` → `Система координат` → `Заготовка, инструменты` → `Область обработки` → операции `Фрезерование dX`;
- добавление, удаление, переименование, переупорядочивание узлов, контекстное меню;
- **инструменты** — отдельный справочник, один инструмент используется несколькими операциями;
- **операции** — T, S, F, припуск, шаг по Z, шаг по Ae, безопасная высота; траектория выбранной операции показывается на 3D‑модели;
- **УП** — G‑код с трохоидальными петлями и предпросмотром в симуляторе;
- **проект `.tcplan`** — план вместе с геометрией, открывается и восстанавливается целиком;
- **строка статуса** — увеличена до 14 px, выделяемая и копируемая (кнопка «Копировать»), чтобы текст ошибки можно было прислать целиком.

### 2.3. Почему приложение падало и что изменилось

| Этап | Подход | Итог |
|---|---|---|
| 1 | Прямое позднее связывание по объектной модели API 7 (`TopPart.ModelObjects(6)`) | `DISP_E_UNKNOWNNAME`: у `IPart7` нет `ModelObjects` |
| 2 | `QueryInterface` к `IFeature7` + вызов через фиксированные слоты vtable | **Фатальное падение**: `IFeature7` — не dual‑интерфейс, слот 5 занят другим методом. Вызов уходит в чужой код и портит стек; `ExecutionEngineException` перехватить нельзя |
| 3 | **API 5** (`KompasObject`), где все интерфейсы Automation‑совместимые | Работает; подтверждено заказчиком |

Вывод, который стоит зафиксировать на будущее: **для интерфейсов API 7 нельзя вызывать методы по номерам слотов vtable**. Если понадобится API 7 — только через библиотеку типов (`KompasLib`/`gencache`‑аналог) или через готовые типизированные обёртки.

### 2.4. Надёжность

- Каждый COM‑вызов изолирован: сбой одного метода (например, одного ребра) не прерывает чтение модели и не роняет процесс.
- `Connect` и `RefreshGeometry` ловят исключения и показывают их в строке статуса, а не закрывают приложение.
- Необработанные исключения дописываются в **`crash.log`** рядом с `KompasTrochoidCam.exe` — если что‑то всё же упадёт, останется след со стеком.
- Неподтверждённый API 5 не кэшируется: при следующем «Обновить геометрию» проверка повторяется (документ могли открыть уже после подключения).
- Подробный лог чтения складывается в окно «Диагностика»: результат подключения API 5, сколько тел в `BodyCollection`, сколько граней найдено, сколько отброшено (без циклов / не горизонтальные), габариты.

## 3. Ограничения текущей версии

1. **Только горизонтальные плоскости.** Наклонные и вертикальные грани игнорируются — это осознанное решение для 2.5D по Z‑уровням.
2. **Только активный документ и его главный компонент.** Сборки не обходятся: компоненты сборки не читаются.
3. **Система координат — детальная.** ЛСК и преобразования не применяются.
4. **Точность аппроксимации фиксирована:** шаг полигона 0.2 мм, допуск горизонтальности 0.05 мм, склейка концов 0.5 мм.
5. **Дуги — только окружности.** Сплайны и эллипсы остаются полилиниями (для УП это допустимо, для «красивых» дуг в G‑коде — нет).
6. **Чтение синхронное, в UI‑потоке.** На крупных моделях окно «подвисает» на время чтения; индикатора прогресса нет.
7. **Полное перечитывание модели** при каждом обновлении; кэша нет.
8. **Зависимость от `KOMPAS.Application.5` в ROT.** Если в системе этот ProgID недоступен, геометрия не прочитается: мост через `TransferInterface` не реализован.
9. **Нет автотестов** — проверки геометрии, области и УП выполняются вручную.

## 6. Если что‑то пошло не так

Пришлите, пожалуйста, четыре вещи — этого обычно достаточно, чтобы найти причину без переписки:

1. **Текст строки статуса** (выделить → «Копировать»).
2. **Отчёт «Диагностика»** — кнопка в окне; там пошаговый лог: какой ProgID сработал, доступен ли `ActiveDocument3D`, сколько тел и граней нашлось.
3. **`crash.log`** из папки с `KompasTrochoidCam.exe` — если приложение всё‑таки упало.
4. **Что делали** (какая кнопка, какая деталь) и версия КОМПАС.

| Параметр | Значение | Где |
|---|---|---|
